npm supply-chain auditing

A package isn’t dangerous because its code looks wrong.

It is dangerous because we wrote down a specific accusation, built a trap designed to provoke exactly that, ran the package inside it — and then had to point at the lines of the recording that prove it happened.

See how a verdict is made What the verdicts mean

● Suspicion is cheap. Proof is the product.

Why this is hard

Installing a package is a decision to run someone else’s code.

Not to read it. Not to import it. To run it — on your laptop, with your credentials sitting on disk, before a single line of your own code executes.

It runs before you use it

A package can ask npm to execute a script the moment it is unpacked. You never imported it. You never called it. It ran anyway.

Bad code looks like good code

Reading a config file is normal. Reading a config file that happens to hold your credentials is not. The two lines are indistinguishable until you know what the package is for.

“Looks suspicious” is not a finding

A scanner that flags everything unusual is a scanner nobody reads. If a warning cannot point at something that actually happened, it is an opinion with a red icon on it.

The whole idea

We accuse first, then build the conditions that would make the accusation come true — and only call it proven if the recording says so.

Every stage that follows exists to produce accusations specific enough to be tested, and to test them. Nothing in the pipeline is allowed to declare a package dangerous on impression alone.

How a verdict is made

Six steps, and two places it can stop early.

We follow one package the whole way down: chalk-utils, a library that claims to colour terminal text.

STEP 01

Get the real files

Download the exact tarball the registry would hand you and unpack it somewhere harmless. Then take mechanical inventory: what files exist, which are actually programs, and which of them npm has been told to run on install.

Nothing is judged here. This step only turns a name into a pile of files that later steps can read.

3 files · 1 install hook · 0 binaries

STEP 02

Work out what it’s supposed to do

Read the README and the manifest and write down, in one sentence, the package’s own pitch — plus the short list of powers that pitch would justify.

This is the baseline everything is measured against. “Opens a network connection” is the entire point of an HTTP client and an anomaly in a string formatter. Without the pitch, the same line means nothing. If this step fails, the list of justified powers is empty — which makes the audit more suspicious, never less.

README.md

“chalk-utils gives you tiny helpers for colouring terminal output. No dependencies, no build step.”

what it is for

powers this justifies: none

a pure string library needs no files and no network

STEP 03

Read every file against that pitch

One pass per source file, each one holding the package’s own stated purpose. The output is not a score — it is a short list of exact line numbers and a sentence saying what is wrong with them.

A suspicion that can’t point at a line is thrown away. Line numbers are checked against the real file, so a suspicion about code that doesn’t exist never survives.

STEP 04

Turn each suspicion into an experiment

“This looks wrong” becomes “this specific thing will happen, and here is how to make it happen.” Plant the bait the code is reaching for. Fake the conditions it is waiting for. Then invoke exactly one entry point.

The bait is the trick. We plant a credential nobody else has. If that exact string later leaves the machine, the link between “read a file” and “sent it somewhere” is demonstrated, not inferred.

plant~/.npmrc = CANARY_f8e2d91a
fakea1-metrics.io → 200 ok
freezeclock, so time-gated code fires
trigger › scripts/setup.js

every experiment ends in exactly one trigger

STEP 05

Run it, with four sensors watching

The package executes for real, in a throwaway container, on a writable copy of itself. Four independent recorders watch at once, at four different depths. What comes out is a sealed, tamper-evident recording of everything that happened.

There is no cheap mode. Every accusation gets every sensor — because clearing a package on a partial recording would be a lie.

STEP 06

Judge it — with citations, or not at all

The recording is rendered as a numbered timeline. A judge answers one question: did the accused behaviour happen? A “yes” must cite the exact event numbers that show it.

An accusation with no pointer to the record is not an accusation. A verdict that cites nothing, or cites events that don’t exist, is rejected before anyone sees it.

“This is clearly malicious behaviour.”
rejected — cites nothing
“The planted token was read from ~/.npmrc and sent in a POST to a host unrelated to terminal styling.”
Dangerous e2 e5 e6

It can stop at step 01

Some packages settle the question structurally: they pipe a script off the internet straight into a shell, or their install hook runs a file that isn’t in the package. In both cases what actually executes is decided somewhere else, so auditing the contents proves nothing. That is dangerous on its face, and no further work is done.

It can stop at step 03

If every file was read against the package’s own stated purpose and not one of them produced an accusation, there is nothing to test. The sandbox never starts. That is the quiet, common, correct outcome for the overwhelming majority of packages.

Inside the sandbox

Four recorders, because one can be fooled.

Malware hides from the thing watching it. So we watch from four independent depths at once. Defeating one leaves the other three untouched.

Depth 1

The kernel

Every request the program makes of the operating system: files opened, bytes written, connections dialled.

Depth 2

The wire

Raw packets leaving the box — the names it looked up and the requests it actually sent.

Depth 3

The disk

A before-and-after photograph of the filesystem. Anything created, changed or deleted shows up in the difference.

Depth 4

The runtime

Inside the JavaScript engine: which built-ins were called, and any code the package assembled at runtime that never existed as a file.

If the sensors go quiet, that is not an acquittal.

A package that suppresses the instrumentation produces a recording we cannot trust. That outcome is recorded as “we did not observe this” — never as “nothing happened.”

The outcome

Two verdicts — and one honest refusal to give one.

Dangerous

We saw it happen.

At least one accusation was written down in advance, provoked on purpose, and confirmed by a judge pointing at numbered lines of the recording. Or the package settled it structurally at step one.

Backed by
A stored, content-hashed recording you can replay.
Safe

Nothing we could confirm.

Either no file produced an accusation, or every accusation raised was compiled into an experiment, run to completion with all four sensors intact, and shown not to happen.

Always shipped with
How many suspicions were raised, and that all of them ran.
Could not conclude

We tried, and failed.

A sensor failed, the run was cut short, or a step errored. There is no report. You are told the audit could not be completed and invited to retry.

Never
Quietly rounded down to “Safe”.

“Safe” does not mean this package is safe.

It means this audit found nothing it could confirm. Missing a threat is a product failure; overstating a clean result is a credibility failure, and credibility is the whole product. So a clean result is the quietest state in the system — stated flatly, always beside its coverage, never celebrated. One accusation we could not evaluate is enough to deny it.
